# A better way wins

A project is defined by what it sets out to achieve, not by the first way someone thought of building it.

Whatever is written about its design, architecture, tools or execution describes the current approach. It can change. If another method gets the intended result better, that method can replace part of the design or the whole thing. It can also combine good parts of several approaches.

A proposed replacement should be judged by what it actually achieves: quality of the result, usefulness, reliability, speed, cost, simplicity, and any other factors that matter to that project. “Newer” alone does not mean “better.” Preserve the project's purpose and the capabilities that make it valuable. Change those deliberately when the project's goals change.

This applies to every project, invention, disclosure, prototype, workflow and future development. A description of one way of doing something is an example, not a restriction to that way.

When publishing a changed or newly invented method, document it and date it in its own right. Keep the earlier public record intact. A general statement about future improvements does not by itself establish patent rights or an earlier priority date for inventions that have not yet been disclosed.

## For the people and agents building these projects

Follow the intended result. Use the best supported way to reach it, including a different architecture when that is the better solution. Verify the outcome rather than treating a previous implementation as sacred. Keep authorship, source history, existing commitments and relevant interfaces traceable as the implementation evolves.

## Use in individual repositories

Each project's README should carry a short, self-contained version of this rule and link here. Independent public specifications should state the rule in their own text as well.
